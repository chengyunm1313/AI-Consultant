    最近看到一位開發者分享自己的 AI 工作流，讓我覺得很有意思。 依照那則分享，他買了三台 Mac，使用兩個 Claude Code 高階訂閱帳號，總共執行八個 AI Agents。每個 Agent 都有自己的 Tart 虛擬機，再透過 Herdr、Tailscale 和 Claude Code Remote Control，讓整套系統可以遠端操作、長時間執行。 他的工作包含開發、寫書、製作講義、簡報、研究新技術，甚至整理郵件與 AI 新聞。這些工作逐漸從自己動手，變成由 AI Agent 負責。 而且不只是坐在電腦前操作，出差在外也能透過手機或筆電，接手原本正在執行的工作。 看到這裡，我開始思考：我們真的需要三台 Mac、八個 Agent，才能打造自己的 24 小時 AI 團隊嗎？ 研究之後，我發現答案是不一定。真正值得學習的，是這套架構背後的設計思維。 這篇就來拆解核心技術、實際安裝方法、成本，以及如何利用現有設備，打造自己的 24×7 AI Agent 工作站。 閱讀範圍：開場的設備數量、訂閱數量與工作內容，是作者轉述的開發者分享；本文未取得原始分享連結，並非本文實測紀錄。以下安裝步驟供讀者實作驗證；Dispatcher 與跨設備接力流程屬於延伸設計，不是安裝工具後就會自動具備的功能。 一、24×7 AI Agent 和一般 AI 助手差在哪裡？我們平常使用 ChatGPT、Claude、Gemini，大部分都是這樣： 打開聊天介面。 輸入問題或交代工作。 等待 AI 回答。 自己檢查結果。 再交代下一件事。 這種模式比較像是「AI 助手」。24×7 AI Agent 則像是一個隨時待命的數位工作團隊，例如可以規劃這樣的工作日： 時間 Agent 預期工作 早上六點 研究 Agent 整理昨天的重要 AI 新聞 早上七點 教材 Agent 根據研究結果，產生技術教學文章草稿 早上八點 開發 Agent 檢查 GitHub 專案、執行測試並整理異常 下午 影音 Agent 處理影片素材、字幕及剪輯工作 晚上 幕僚長 Agent 彙整成果，產生每日報告 你不需要一直坐在電腦前面盯著它們。不過，24×7 在線，不等於 AI 真的會自動工作。 要做到真正的自動化，至少需要五個部分： 持續運作的電腦或伺服器。 能執行工作的 AI Agent。 排程或事件觸發機制。 任務管理與失敗重試機制。 遠端監控及通知機制。 少了其中幾個，可能只是讓 AI 一直開著，卻沒有真正提高工作效率。 二、先認識五個核心工具，各自解決什麼問題？1. Claude Code：負責工作的 AI 員工Claude Code 是 Anthropic 推出的 AI Coding Agent。雖然名字裡有 Code，但它不只能寫程式。 只要工作能透過檔案、指令、API 或其他支援的工具完成，就有機會交給它處理，例如： 開發網站與應用程式、修改 GitHub 專案。 撰寫 Markdown 教材、整理研究資料及產生簡報內容。 執行 Python 程式、批次處理文件。 操作已設定且支援的外部工具。 與一般聊天式 AI 最大的差別，是 Claude Code 可以直接在工作環境中執行操作。例如你交代： 幫我檢查這個網站專案，把錯誤修好，測試通過後整理修改報告。 它可以讀取程式碼、修改檔案、執行測試，再回報結果；前提是你已提供適當的工作環境、工具與權限。 2. Herdr：集中管理整隊 Agent 的工作階段如果你同時開啟好幾個 Claude Code、Codex 或 OpenCode，可能會遇到這種情況：一個視窗正在寫程式、另一個跑測試、第三個等待回答，第四個則不知道什麼時候已經失敗。最後，你花很多時間切換視窗、檢查進度。 Herdr 就是想改善這類問題。它能集中管理多個 Agent 的終端機工作階段；但必須先分清楚目前官方的兩條產品路線： Herdr TUI：終端機介面，使用自己的背景 server；本文的 herdr 指令與 herdrdev&#x2F;herdr repo 屬於這條路線。 Herdr App、手機 App 與 Herdr Core：另一套以 Core 管理工作階段的架構，須依對應文件設定。官方首頁說明，TUI 與 App 不共用 Agent，不能假設 TUI 開出的工作階段會直接出現在 App。 Herdr TUI 的主要能力包括： 能力 實際意義 工作階段持續存在 終端機關閉或 SSH 中斷後，背景 server 可維持窗格內的程序；主機關機仍會中斷工作 跨電腦管理 透過 SSH 連接其他設備上的工作階段，仍須具備連線與驗證條件 Agent 狀態監控 在支援的整合與狀態回報機制下，辨識工作中、閒置或等待輸入等狀態 程式化操作 提供 CLI 與 Socket API，讓其他程式管理窗格及工作階段 這些介面讓另一個 AI Agent 有機會參與協調工作。不過，Herdr 的工作階段管理不能直接取代完整的任務排程、持久化佇列、重試、權限審核與成果驗收。 功能與指令請以安裝版本的 TUI 文件及 Socket API 文件為準。 3. Tailscale：讓不同電腦建立私人連線假設你有家裡的 Mac、辦公室的 Windows，以及 Oracle Cloud 上的 Linux VM。這三台設備可能位於不同網路。 傳統做法可能需要處理固定 IP、Port Forwarding、防火牆與 VPN。Tailscale 利用 WireGuard 技術簡化私人加密網路的建立。設備加入同一個 Tailnet，並符合存取權限設定後，就能透過私人網路連線。 你可以人在外面用筆電連回家裡的 Mac，或讓雲端 Linux 連接辦公室的 Windows。不過，Tailscale 負責的是網路連線，Agent 的啟動與派工仍要另外設定。 4. Tart：在有需要時提供獨立虛擬機Tart 是針對 Apple Silicon 設計的虛擬機管理工具，可以執行 macOS 與 Linux VM；原始碼位於 cirruslabs&#x2F;tart。 開場分享採用的方式，是讓不同 Agent 在各自的 Tart VM 工作。這能減少環境衝突，例如 Agent A 安裝 Node.js 套件、Agent B 修改 Python 環境、Agent C 更新系統設定時，不必全部共用同一套作業系統環境。 但虛擬機需要額外 CPU、記憶體與磁碟空間。如果 Mac 只有 16GB RAM，我不建議一開始就替每個 Agent 建立一台 VM。 比較實際的方式，是先用不同工作目錄搭配 Git Worktree；確實需要隔離作業系統或相依套件時，再考慮 Tart。使用前也應確認所選版本的授權與使用條件，不把「可查看原始碼」直接當成所有用途都免費或無限制。 5. Claude Code Remote Control：人在外面也能接手假設 Claude Code 正在家裡的 Mac 工作，而你已經出門。當它需要確認下一步時，可以透過 Remote Control，從支援的 Claude 網頁或手機介面接續本機工作階段。 在 Claude Code 裡可以輸入： 1/remote-control 實際執行的仍是原本的電腦，電腦必須保持開機、Claude 程序持續運作且能連網。休眠或網路中斷時會影響可用性，恢復後的重新連線行為也要實測。 可用性受到訂閱、登入方式、組織政策與版本影響；目前官方文件說明 API key 不支援 Remote Control，使用前應查看最新需求。它與透過 Tailscale 建立 SSH 連線是兩條不同的遠端操作路徑，啟用 Remote Control 本身不要求先安裝 Tailscale。 新聞、GitHub 研究 Linux VM Developer 網站開發、程式測試 Mac Writer 教材、文章、講義 Mac Media 影片、字幕、轉檔 Windows 再建立 Dispatcher 負責派工。例如你交代： 研究最近一週值得教學的 AI Agent 開源專案，選出三個，產生教學文章，最後更新課程網站。 Dispatcher 可以拆成三個有依賴關係的任務： 任務 A：研究。 接力工作流。但要做到這件事，還需要真正的任務管理系統，可以使用 SQLite、PostgreSQL、Redis 或適合的持久化佇列方案。 最基本的任務資料可以長這樣： 12345678910111213&#123; &quot;task_id&quot;: &quot;TASK-001&quot;, &quot;title&quot;: &quot;研究 AI Agent 開源專案&quot;, 減少多邊形數量 不保證減完就適合變形動畫 Retopology（重新拓樸） 重新安排網格結構 更重視後續編輯、變形或烘焙需求 如果模型太複雜，後續修改、骨架設定與即時渲染都會增加成本，遊戲資產尤其需要控制複雜度。不過，只製作靜態圖片時，不一定值得花大量時間重新拓樸；以剛體零件為主的機甲，也不需要每片裝甲都使用真人角色的變形佈線。 整理到什麼程度，取決於最終用途。 四、Step 4 的法線貼圖，應該在哪個階段使用？假設我們已經生成一台精細機甲，胸甲有螺絲、散熱孔、裝甲接縫、金屬刻痕。如果全部使用真正幾何呈現，模型可能相當複雜。 其中細小刮痕、淺凹槽、在目標觀看距離下不影響輪廓的螺絲頭，可以考慮用法線貼圖模擬。這就衍生出常見的遊戲資產製作方法： High Poly → Low Poly → Normal Map，也就是高精度模型 → 低面數模型 → 烘焙法線貼圖。 假設先做一台有 100 萬個多邊形的精細機甲，再製作只有 2 萬個多邊形的簡化版本。這些數字只是示意，不是所有機甲的標準面數。 簡化後，原本的螺絲、細刻痕可能消失。這時透過 Baking（烘焙），把高模的表面方向細節轉成適用於低模的法線貼圖，再套回低模材質。 低模雖然沒有那些真正的小幾何，在光線下仍能呈現類似凹凸。這能降低幾何成本、保留許多視覺細節，也方便配合不同精細程度的模型版本。但總效能仍受貼圖記憶體、材質數量、繪製次數等因素影響，不能只比較面數。 法線貼圖不能取代哪些結構？法線貼圖不會真正改變物體輪廓。 例如肩膀上有一根長砲管，不能只靠法線貼圖讓它伸出來。大型裝甲、武器、推進器、真正的開孔與活動關節，仍然需要合理的幾何結構。 它也不會替模型增加碰撞體積；當細節需要影響輪廓、接觸或近距離視差時，就要重新評估是否應保留幾何。 AI 生成法線圖，等於高低模烘焙嗎？不等於。 AI 可以生成看起來合理的表面凹凸，但要精準保留特定高模的細節，仍需要高低模對應、低模 UV 與正式烘焙流程。不能把任意一張紫藍色圖片直接當成正確法線資料。 在 Blender 中，法線圖通常會經過 Normal Map 節點再接入材質。切線空間法線圖需要對應的 UV，圖片應設定為 Non-Color，並確認與目標引擎的法線慣例相容。可參考 Blender 官方 Normal Map 節點手冊與烘焙說明；實際介面請對照自己使用的 Blender 版本。 五、Step 4 的材質與 UV，跟法線貼圖有什麼關係？法線貼圖其實只是材質系統的一部分。在 3D 製作中，常見的是 PBR（Physically Based Rendering，物理基礎渲染）材質。 用機甲來理解： 項目 用途 機甲範例 Base Color 決定基本顏色 紅色裝甲、白色胸甲、黑色關節 Metallic 表達金屬特性 金屬裸露區與非金屬塗層的差異 Roughness 控制反射的粗糙程度 低粗糙度反射較銳利，高粗糙度較模糊 Normal 模擬細小凹凸 刻痕、淺凹槽與裝甲紋路 Emission 表達自發光外觀 眼睛、能源核心與燈條 金屬零件表面若覆有一般非金屬漆，不能只因底下是金屬，就把整片外觀都設成裸金屬。Emission 能讓表面看起來發光，但是否照亮周圍、是否產生光暈，還取決於渲染器、燈光與後製設定。 UV 展開是什麼？想像把紙盒拆開攤平成一張紙，在紙上印上顏色與圖案，最後再折回紙盒。 UV 展開建立 3D 模型表面與 2D 圖片的對應關係。如果 UV 不正確，材質就可能拉伸、錯位或出現接縫。 因此，完整材質流程通常是： 模型整理 → UV 展開 → 產生或烘焙貼圖 → 設定 PBR 材質 → 檢查成果。 這也解釋了原本「使用 GPT 生成材質貼圖」需要補上的條件：產生一張金屬紋理圖片，不等於已經完成這台機甲的材質。 圖片仍要對應 UV，或經過投射、接縫修整與烘焙；Base Color、Roughness、Metallic、Normal 也必須各司其職。不能把帶著固定高光與陰影的彩色圖片，直接當成完整的 PBR 貼圖組。 「貼圖只能 512K」是什麼意思？原分享提到的「512K」需要特別注意，因為這不是清楚的貼圖像素尺寸寫法。它可能想表達 512×512 像素，也可能在描述檔案容量；沒有原始規格，無法確定。 兩者差異很大，而且貼圖解析度也不是越低越好： 常見像素尺寸 可以考慮的情境 512×512 部分小型物件或遠距離資產 1024×1024 部分一般中小型資產 2048×2048 需要較多近距離細節的資產 4096×4096 高細節需求，同時承擔較高記憶體成本 這些只是示意，不是固定標準。應考慮觀看距離、螢幕佔比、平台效能、貼圖數量與材質需求，也要區分磁碟壓縮檔大小與 GPU 載入成本。 不能直接說「不是做電腦遊戲，就只能使用 512 的貼圖」。 六、Step 5 為什麼要拆關節，還要設定骨架？因為目前做出來的機甲，可能只是一個外觀完整的模型。要讓它走路，就必須建立合理的活動結構。 機甲跟真人角色的綁定方式不完全相同。真人手肘彎曲時，皮膚會變形；但機甲的金屬裝甲，正常情況下不應該像橡皮一樣彎曲。 所以通常要讓不同部位可以獨立控制，例如胸甲、上臂、前臂、肩關節、大腿、小腿、膝關節與腳掌。這些可以是分離物件，也可以是同一網格內彼此不連通、由不同骨骼控制的剛體區塊。 接著設定旋轉樞紐、父子階層與活動限制： 手肘在合理角度內彎曲。 膝蓋不隨意向後折。 肩膀轉動時，肩甲配合移動。 腳掌落地時維持合理的接觸位置。 如果只把表面切開，沒有補齊遮住的零件、關節間隙與樞紐，動起來仍可能穿模或露出破洞。 有些機甲只需分離零件、旋轉樞紐與父子階層，就能完成基本動作；若使用骨架，也可以讓剛性裝甲跟隨單一骨骼，不一定要像皮膚一樣做平滑蒙皮變形。軟管、線材等需要彎曲的部分，則另行處理。 **機甲建模還涉及機械結構與運動設計。**拆分不正確，即使外觀很漂亮，動畫仍可能很奇怪。 Step 6：製作動畫，並到引擎中驗收骨架設定完成，還要在時間軸上安排動作。先從抬手、屈膝、腳掌落地等簡單測試開始，再做完整走路循環。 過程中要觀察裝甲是否穿模、腳是否滑動、重心是否合理，以及匯出後的骨架、材質與動畫是否一致。最後匯入 Godot 或其他目標環境，確認尺度、方向、播放與效能，才算走完這條流程。 能在 Blender 裡播放，不代表已完成遊戲整合；遊戲中的移動控制、碰撞與動畫切換，也需要另外設定與測試。 七、三種 AI 3D 建模流程，應該怎麼選？研究到這裡，我認為應該先決定用途，再選製作流程。 方案 A：快速展示型AI 圖片 → AI 生成白模 → AI 材質 → 3D 展示。 適合科幻角色展示、產品概念設計、靜態渲染與社群作品。若用於 3D 網頁，仍要視模型大小和裝置效能做適度整理。 優點是速度快、操作相對簡單；缺點是模型不一定適合動畫或遊戲。如果只想展示漂亮機甲，先走這條就很合理。 方案 B：遊戲資產最佳化型AI 圖片 → 高精度模型 → 整理低模 → UV → 烘焙法線貼圖 → PBR 材質。 適合遊戲場景物件、即時 3D、WebGL 展示，以及需要控制效能的資產。 優點是兼顧細節與幾何複雜度；缺點是需要理解 UV、拓樸與烘焙。這套流程不會自動讓機甲動起來。 方案 C：可動機甲型AI 圖片 → AI 生成白模 → 零件拆分與整理 → 關節設定 → 骨架／控制系統 → 材質 → 動畫。 適合機甲動畫、遊戲角色、戰鬥機器人與互動展示。優點是能建立真正可動的機甲；缺點是關節與動畫需要仔細調整，技術門檻最高。 這裡的排列是概念路線，不是唯一施工順序。需要改拓樸或拆件時，應先規劃好再定稿 UV 和烘焙；也可以先做簡單活動測試，再投入精細材質。 我認為比較合理的做法，是先建立幾個核心角色： AI 角色 主要職責 可以驗收的交付物 AI 幕僚長 任務管理、進度追蹤與工作分派 任務清單、負責角色與進度摘要 AI 研究員 蒐集資訊、研究技術與驗證資料 附來源的研究筆記與待確認事項 AI 內容編輯 文章、社群貼文與行銷素材 可審閱的內容草稿 AI 工程師 開發工具、建立自動化流程 可執行的程式與驗證紀錄 甚至不一定需要四個獨立的 Bot。如果系統能妥善管理角色、上下文與權限，也可以由一個主要 Agent，根據任務切換不同的專業角色。 但角色切換不等於權限隔離。如果不同工作需要不同的資料存取或核准規則，仍要確認平台能否真正限制權限。 重點從來不是 Agent 的數量，而是工作能不能被正確完成。 如果你還在釐清聊天工具與代理的差異，可以先閱讀AI 聊天機器人與 AI Agent 的差別。 二、如何把 AI 的成功經驗，整理成可重用的 Skills？這是我特別喜歡的觀念：當你教 Bot 執行某項任務時，可以要求它把成功的工作流程整理成 Skills。 為什麼？因為 AI 有一個很常見的問題：今天教會它的事情，過了一段時間，換個對話或執行環境，可能又得重新說明。尤其當工作涉及很多細節時，光靠一大段提示詞，很難保證每次執行都一致。 這時候，Skills 就非常有價值。 例如，我經常需要將 AI 技術研究整理成部落格文章，再改寫成 Facebook 粉專貼文。與其每次重新交代「幫我研究技術背景、確認資料、加入實際應用案例，再改成適合粉專閱讀的語氣」，不如把這些步驟整理成一套內容製作 Skill。 以後只要告訴 AI： 使用我的科技文章 Skill，研究這個主題。 在支援這套 Skill、具備必要工具與資料權限的環境中，AI 就能依照既定流程執行。 一套實用的 Skill，至少應該交代： 什麼情況要使用，以及需要哪些輸入資料。 工作步驟與判斷規則。 預期輸出格式與驗收標準。 遇到缺漏或錯誤時如何回報。 哪些操作需要人類核准。 這些要素也與 Grok Bot 官方文件對 Skill 的說明一致：先完成一次任務、修正到可靠，再保存工作方法，最後才考慮自動化。 更進一步，也可以把不含機密或個資的 Skills 集中儲存在 GitHub 私有儲存庫，透過版本管理持續改善；實際載入與同步方式則取決於所用平台。 這其實就是企業很熟悉的 SOP（標準作業程序）。以前我們把工作經驗寫成 SOP，交給新人學習；現在可以把 SOP 整理成 Skills，交給 AI Agent 執行。想進一步整理自己的方法，可以參考從 Prompt 走向 Skill 工作流。 但也要注意：Skills 不保證 AI 永遠不會出錯，仍然需要測試、驗收與持續修正。 三、哪些工作交給 AI Agent，哪些應該寫成 Scripts？另一個值得深入研究的方向，是請 Bot 幫你寫程式，把重複性的工作流程自動化。 這個做法看似簡單，背後卻牽涉到 AI Agent 的成本與架構設計。 假設每天都要處理 100 封訂單郵件。如果讓 AI Agent 每次都打開信箱、閱讀郵件、擷取欄位、開啟試算表、填入資料，每個步驟都需要模型判斷，可能消耗大量 Tokens，也增加執行時間。 但換個方式呢？ 第一次先請 AI Agent 分析工作流程，幫忙寫好 Script。之後透過程式自動讀取授權範圍內的郵件、解析固定格式、整理訂單資料。只有遇到格式不一致、資訊缺漏或需要判斷的情況，才交給 AI Agent 處理。 這種設計有機會減少重複的模型呼叫，讓固定步驟更容易檢查；實際成本與穩定性仍要依郵件格式、錯誤率與維護需求驗證，不能只看 Token 數量。 我認為比較成熟的架構，可以這樣分工： 組成 負責什麼 訂單情境中的例子 AI Agent 思考、規劃與處理例外 判讀不規則來信、列出缺漏資訊 Scripts 固定且重複的執行 擷取固定欄位、去除重複紀錄、產出資料表 Skills 保存工作方法與驗收規則 定義訂單欄位、核對步驟與人工確認條件 自動化流程 決定何時啟動、如何交接 收到符合條件的郵件後啟動處理 三者互相搭配，再由自動化流程串起來，而不是什麼事情都丟給大型語言模型。 這也是為什麼我最近越來越重視 Codex、Cloudflare、GitHub 與各種自動化工具的整合。因為 AI 最有價值的地方，不只是幫你完成一次工作，而是幫你建立一套以後可以持續運作的流程。 四、如何用 Routines，讓 AI 在適當的時間主動工作？Routines 可以理解為例行任務。依 Grok Bot 官方工作指南，它可以依排程，或在支援的事件發生後啟動工作。 排程型：在指定時間執行例如每天早上八點，檢查授權的信箱、整理重要訊息、確認行事曆，並產出今日工作摘要。 事件觸發型：符合條件才開始工作例如當指定客戶寄來新郵件，AI 自動整理需求、更新允許修改的客戶紀錄，並準備回覆草稿。可用的事件來源與連接器，仍要以平台實際支援為準。 這兩種模式讓工作方式出現變化：以前我們要記得叫 AI 做事，現在可以讓系統在適當的時間，或特定事件發生時，自動開始工作。 但這裡也有一個很重要的管理問題：不是所有工作都需要每五分鐘檢查一次。觸發太頻繁，可能增加成本，也可能產生大量重複資訊。 所以我認為，設計 AI 自動化時，應該先思考三件事： 這件事情需要多即時？ 有沒有辦法先過濾不重要的事件？ 哪些結果需要人類確認才能執行？ 例如一般新聞整理，每天執行一次可能就夠了；重要客戶的緊急需求，則可能需要更即時的通知。只有出現值得處理的變化時再通知，也能減少干擾。 真正好的 AI Agent，是知道什麼事情值得做、什麼時候該做。 五、如何像培訓新同事一樣，讓 AI 正確完成任務？我們也可以用一個問題檢查自己的管理方式：如果今天聘請一位實習生，你會如何讓他熟悉工作，並確保他能正確完成任務？ 假設公司來了一位新員工，你會不會只跟他說「幫我把公司行銷做好」，然後就期待他自己把所有事情完成？應該不會吧！ 你至少會告訴他：公司是做什麼的、客戶是誰、有哪些工作流程、可以使用哪些工具、什麼事情需要主管核准，以及完成工作的標準是什麼。 但很多人在使用 AI Agent 時，卻只給它一句簡單的提示詞。發現結果不理想，就認為 AI 不夠聰明。問題可能不只在模型能力，也在於我們沒有提供足夠的工作背景與驗收標準。 這也是為什麼我認為，企業導入 AI Agent，不能只停留在提示詞教學，還需要建立： 工作角色與職責。 知識庫與 Skills。 工具使用權限。 標準作業流程。 任務驗收與錯誤回報機制。 以客戶回覆為例，「幫我處理客戶郵件」太籠統。比較清楚的交代是：整理來信需求、標示需要補問的資訊、依範本產出回覆草稿，完成後交給我審核，取得核准才寄出。 尤其涉及客戶資料、金流、對外發送訊息等工作，更需要明確的權限與審核制度。 AI Agent 可以自主執行工作，但自主不代表不需要管理。 六、下一階段的競爭，為什麼是 AI 管理能力？回頭看看這幾年的 AI 發展：最早大家比的是誰比較會寫 Prompt，後來比的是誰會使用更多 AI 工具，接著開始比誰會使用 AI Agent、誰會建立自動化流程。 但我認為，接下來真正拉開差距的，可能是另一種能力： 你能不能把自己的工作方法，轉換成一套 AI 可以持續執行、持續改善，而且能夠驗證成果的系統？ 例如我現在要製作一門 AI 課程。理想中的工作方式，是告訴 AI 幕僚長： 我要規劃一門六小時的 AI 實戰課程，對象是沒有技術背景的企業學員，希望每個人最後都能完成實際作品。 接著由 AI 研究員整理工具與案例、AI 教學設計角色規劃課程、AI 工程師建立互動式教學網站、AI 內容編輯準備招生文案。每個階段都要有清楚的輸入、交付物與交接條件。 最後由我檢查課程品質、調整教學策略、決定正式版本。這才是我期待的 AI 工作模式。 當然，這不代表目前每一套 AI Agent 平台都能完整做到，也不代表可以完全不需要人工介入。但這個方向值得持續實驗：我們正在從「使用 AI 工具」，走向「管理 AI 工作系統」。 從今天開始，先盤點這五個問題不要急著問自己還能建立多少個 AI Agent，先問問自己： 我每天有哪些工作，一直在重複做？ 哪些工作方法，可以整理成 Skills？ 哪些固定流程，可以直接寫成 Scripts？ 哪些事情，可以交給 AI 自動監控與處理？ 哪些決策，仍然需要我親自把關？ 當你開始用這樣的方式思考，就已經開始扮演一位 AI 團隊的管理者。 未來，真正有價值的可能不是一個人會操作十種 AI 工具，而是這個人能不能帶領一支由 AI Agent、Skills、Scripts 與自動化流程組成的團隊，完成過去需要好幾個人才能完成的工作。 你不需要擁有最多的 AI 員工，你需要的是一支真正能幫你完成工作的 AI 團隊。這才是我認為 AI
