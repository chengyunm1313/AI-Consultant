    最近看到一位開發者分享自己的 AI 工作流，讓我覺得很有意思。 依照那則分享，他買了三台 Mac，使用兩個 Claude Code 高階訂閱帳號，總共執行八個 AI Agents。每個 Agent 都有自己的 Tart 虛擬機，再透過 Herdr、Tailscale 和 Claude Code Remote Control，讓整套系統可以遠端操作、長時間執行。 他的工作包含開發、寫書、製作講義、簡報、研究新技術，甚至整理郵件與 AI 新聞。這些工作逐漸從自己動手，變成由 AI Agent 負責。 而且不只是坐在電腦前操作，出差在外也能透過手機或筆電，接手原本正在執行的工作。 看到這裡，我開始思考：我們真的需要三台 Mac、八個 Agent，才能打造自己的 24 小時 AI 團隊嗎？ 研究之後，我發現答案是不一定。真正值得學習的，是這套架構背後的設計思維。 這篇就來拆解核心技術、實際安裝方法、成本，以及如何利用現有設備，打造自己的 24×7 AI Agent 工作站。 閱讀範圍：開場的設備數量、訂閱數量與工作內容，是作者轉述的開發者分享；本文未取得原始分享連結，並非本文實測紀錄。以下安裝步驟供讀者實作驗證；Dispatcher 與跨設備接力流程屬於延伸設計，不是安裝工具後就會自動具備的功能。 一、24×7 AI Agent 和一般 AI 助手差在哪裡？我們平常使用 ChatGPT、Claude、Gemini，大部分都是這樣： 打開聊天介面。 輸入問題或交代工作。 等待 AI 回答。 自己檢查結果。 再交代下一件事。 這種模式比較像是「AI 助手」。24×7 AI Agent 則像是一個隨時待命的數位工作團隊，例如可以規劃這樣的工作日： 時間 Agent 預期工作 早上六點 研究 Agent 整理昨天的重要 AI 新聞 早上七點 教材 Agent 根據研究結果，產生技術教學文章草稿 早上八點 開發 Agent 檢查 GitHub 專案、執行測試並整理異常 下午 影音 Agent 處理影片素材、字幕及剪輯工作 晚上 幕僚長 Agent 彙整成果，產生每日報告 你不需要一直坐在電腦前面盯著它們。不過，24×7 在線，不等於 AI 真的會自動工作。 要做到真正的自動化，至少需要五個部分： 持續運作的電腦或伺服器。 能執行工作的 AI Agent。 排程或事件觸發機制。 任務管理與失敗重試機制。 遠端監控及通知機制。 少了其中幾個，可能只是讓 AI 一直開著，卻沒有真正提高工作效率。 二、先認識五個核心工具，各自解決什麼問題？1. Claude Code：負責工作的 AI 員工Claude Code 是 Anthropic 推出的 AI Coding Agent。雖然名字裡有 Code，但它不只能寫程式。 只要工作能透過檔案、指令、API 或其他支援的工具完成，就有機會交給它處理，例如： 開發網站與應用程式、修改 GitHub 專案。 撰寫 Markdown 教材、整理研究資料及產生簡報內容。 執行 Python 程式、批次處理文件。 操作已設定且支援的外部工具。 與一般聊天式 AI 最大的差別，是 Claude Code 可以直接在工作環境中執行操作。例如你交代： 幫我檢查這個網站專案，把錯誤修好，測試通過後整理修改報告。 它可以讀取程式碼、修改檔案、執行測試，再回報結果；前提是你已提供適當的工作環境、工具與權限。 2. Herdr：集中管理整隊 Agent 的工作階段如果你同時開啟好幾個 Claude Code、Codex 或 OpenCode，可能會遇到這種情況：一個視窗正在寫程式、另一個跑測試、第三個等待回答，第四個則不知道什麼時候已經失敗。最後，你花很多時間切換視窗、檢查進度。 Herdr 就是想改善這類問題。它能集中管理多個 Agent 的終端機工作階段；但必須先分清楚目前官方的兩條產品路線： Herdr TUI：終端機介面，使用自己的背景 server；本文的 herdr 指令與 herdrdev&#x2F;herdr repo 屬於這條路線。 Herdr App、手機 App 與 Herdr Core：另一套以 Core 管理工作階段的架構，須依對應文件設定。官方首頁說明，TUI 與 App 不共用 Agent，不能假設 TUI 開出的工作階段會直接出現在 App。 Herdr TUI 的主要能力包括： 能力 實際意義 工作階段持續存在 終端機關閉或 SSH 中斷後，背景 server 可維持窗格內的程序；主機關機仍會中斷工作 跨電腦管理 透過 SSH 連接其他設備上的工作階段，仍須具備連線與驗證條件 Agent 狀態監控 在支援的整合與狀態回報機制下，辨識工作中、閒置或等待輸入等狀態 程式化操作 提供 CLI 與 Socket API，讓其他程式管理窗格及工作階段 這些介面讓另一個 AI Agent 有機會參與協調工作。不過，Herdr 的工作階段管理不能直接取代完整的任務排程、持久化佇列、重試、權限審核與成果驗收。 功能與指令請以安裝版本的 TUI 文件及 Socket API 文件為準。 3. Tailscale：讓不同電腦建立私人連線假設你有家裡的 Mac、辦公室的 Windows，以及 Oracle Cloud 上的 Linux VM。這三台設備可能位於不同網路。 傳統做法可能需要處理固定 IP、Port Forwarding、防火牆與 VPN。Tailscale 利用 WireGuard 技術簡化私人加密網路的建立。設備加入同一個 Tailnet，並符合存取權限設定後，就能透過私人網路連線。 你可以人在外面用筆電連回家裡的 Mac，或讓雲端 Linux 連接辦公室的 Windows。不過，Tailscale 負責的是網路連線，Agent 的啟動與派工仍要另外設定。 4. Tart：在有需要時提供獨立虛擬機Tart 是針對 Apple Silicon 設計的虛擬機管理工具，可以執行 macOS 與 Linux VM；原始碼位於 cirruslabs&#x2F;tart。 開場分享採用的方式，是讓不同 Agent 在各自的 Tart VM 工作。這能減少環境衝突，例如 Agent A 安裝 Node.js 套件、Agent B 修改 Python 環境、Agent C 更新系統設定時，不必全部共用同一套作業系統環境。 但虛擬機需要額外 CPU、記憶體與磁碟空間。如果 Mac 只有 16GB RAM，我不建議一開始就替每個 Agent 建立一台 VM。 比較實際的方式，是先用不同工作目錄搭配 Git Worktree；確實需要隔離作業系統或相依套件時，再考慮 Tart。使用前也應確認所選版本的授權與使用條件，不把「可查看原始碼」直接當成所有用途都免費或無限制。 5. Claude Code Remote Control：人在外面也能接手假設 Claude Code 正在家裡的 Mac 工作，而你已經出門。當它需要確認下一步時，可以透過 Remote Control，從支援的 Claude 網頁或手機介面接續本機工作階段。 在 Claude Code 裡可以輸入： 1/remote-control 實際執行的仍是原本的電腦，電腦必須保持開機、Claude 程序持續運作且能連網。休眠或網路中斷時會影響可用性，恢復後的重新連線行為也要實測。 可用性受到訂閱、登入方式、組織政策與版本影響；目前官方文件說明 API key 不支援 Remote Control，使用前應查看最新需求。它與透過 Tailscale 建立 SSH 連線是兩條不同的遠端操作路徑，啟用 Remote Control 本身不要求先安裝 Tailscale。 新聞、GitHub 研究 Linux VM Developer 網站開發、程式測試 Mac Writer 教材、文章、講義 Mac Media 影片、字幕、轉檔 Windows 再建立 Dispatcher 負責派工。例如你交代： 研究最近一週值得教學的 AI Agent 開源專案，選出三個，產生教學文章，最後更新課程網站。 Dispatcher 可以拆成三個有依賴關係的任務： 任務 A：研究。 接力工作流。但要做到這件事，還需要真正的任務管理系統，可以使用 SQLite、PostgreSQL、Redis 或適合的持久化佇列方案。 最基本的任務資料可以長這樣： 12345678910111213&#123; &quot;task_id&quot;: &quot;TASK-001&quot;, &quot;title&quot;: &quot;研究 AI Agent 開源專案&quot;,     最近看到一位 3D 創作者分享，利用 AI 製作機甲模型，一天可以完成 5 台！ 他的製作方式大致是： 找一張喜歡的科幻機甲圖片。 讓 AI 把圖片轉成 3D 白模。 使用 GPT 生成材質貼圖。 把材質貼回 3D 模型。 最後拆分關節，讓機甲可以活動。 看起來好像很簡單，對吧？但我看到這套流程，第一個想到的問題是： 這跟之前研究的法線貼圖有什麼不同？既然 AI 都能生成 3D 模型了，為什麼還需要法線貼圖？又為什麼要拆關節？ 深入研究之後才發現，這其實涉及三種負責不同工作的技術：幾何形狀、表面細節，以及活動控制。它們可以組合成一套完整的 AI 3D 建模工作流。 今天就用製作一台「可以走路的機甲」當範例，從零開始解釋。 「一天 5 台」是本文起點的創作者分享，並非我的實測結果；目前未附該則分享的原始連結，因此不據此推算普遍產能。以下重點是拆解製作流程，以及釐清每個階段的完成標準。 一、3D 白模、法線貼圖與骨架，各自解決什麼問題？先想像我們要製作一台鋼彈。 3D 白模：真正做出立體形狀3D 白模就像拿黏土捏出一台鋼彈。你真的做出了頭部、胸甲、手臂、雙腿，還有背後的推進器。 這個模型可以旋轉 360 度，從正面、側面、背面觀看，因為它具有真正的立體幾何結構。 更精確地說，Mesh 是網格資料；白模則通常指尚未完成材質、以單純顏色檢查形狀的模型狀態。不是所有 Mesh 都是白色，也不是有了白模就代表模型已經適合動畫。 法線貼圖：讓表面看起來有細小凹凸假設鋼彈胸甲上有 100 顆小螺絲。把它們全部建模出來，會增加模型的幾何複雜度。 法線貼圖（Normal Map）利用 RGB 通道編碼表面法線方向，讓著色器計算光照時，呈現螺絲、刻痕、凹槽等凹凸效果。那些細節沒有因此真正凸出來。 換句話說，3D 白模負責真正的形狀，法線貼圖負責模擬細小的表面凹凸。 骨架綁定：建立模型的活動控制現在我們已經有一台外觀漂亮的鋼彈，但它還不會動。模型不會自動知道手肘在哪裡、膝蓋應該怎麼彎曲。 所以我們需要設定骨架、活動關節與旋轉軸，讓它能抬手、轉身、走路，甚至拿武器戰鬥。Rigging 是建立這套控制系統；動畫則是在時間軸上安排具體動作。 技術 解決什麼問題 3D 白模／網格 讓機甲真正具有立體形狀 法線貼圖 用較少幾何結構呈現表面細節 材質與貼圖 決定顏色、金屬感與粗糙程度 骨架綁定／控制設定 建立機甲可以活動的控制方式 動畫 讓機甲在時間軸上做出具體動作 這樣是不是比較容易理解了？ 二、既然 AI 能生成 3D 模型，為什麼還要人工處理？這是整個流程最重要的問題。 現在可以使用 Meshy、Tripo AI、Hunyuan3D 等工具，將圖片轉換成 3D 模型。丟一張科幻機甲圖片給 AI，它可能很快就能生成一台看起來相當完整的機甲。 但看起來像機甲，不代表它真的具備合理的機械結構。 舉個例子，當你想讓機甲舉起右手或走路，可能發現： 肩膀和胸甲黏在一起。 手肘沒有合理的活動空間。 膝蓋彎曲時，裝甲直接穿進大腿。 腳掌沒有正確的支撐點。 走路時雙腳亂甩，整台機甲像章魚一樣。 圖片轉 3D 的 AI 主要在推測外觀與幾何形狀，不一定能建立符合設計意圖的關節、活動限制與運動方式。即使工具提供自動拆件、綁定或動畫功能，也仍然要檢查結果。 所以 AI 生成的模型，經常需要人工整理。這也是為什麼這類工作流仍需要 3D 技術背景：生成速度加快了，後續的判斷與修正並沒有全部消失。 三、如何把 AI 機甲建模拆成完整六步驟？先把整條路線放在一起： 的法線貼圖，應該在哪個階段使用？假設我們已經生成一台精細機甲，胸甲有螺絲、散熱孔、裝甲接縫、金屬刻痕。如果全部使用真正幾何呈現，模型可能相當複雜。 其中細小刮痕、淺凹槽、在目標觀看距離下不影響輪廓的螺絲頭，可以考慮用法線貼圖模擬。這就衍生出常見的遊戲資產製作方法： High Poly → Low Poly → Normal Map，也就是高精度模型 → 低面數模型 → 烘焙法線貼圖。 假設先做一台有 100 萬個多邊形的精細機甲，再製作只有 2 萬個多邊形的簡化版本。這些數字只是示意，不是所有機甲的標準面數。 簡化後，原本的螺絲、細刻痕可能消失。這時透過 Baking（烘焙），把高模的表面方向細節轉成適用於低模的法線貼圖，再套回低模材質。 低模雖然沒有那些真正的小幾何，在光線下仍能呈現類似凹凸。這能降低幾何成本、保留許多視覺細節，也方便配合不同精細程度的模型版本。但總效能仍受貼圖記憶體、材質數量、繪製次數等因素影響，不能只比較面數。 法線貼圖不能取代哪些結構？法線貼圖不會真正改變物體輪廓。 例如肩膀上有一根長砲管，不能只靠法線貼圖讓它伸出來。大型裝甲、武器、推進器、真正的開孔與活動關節，仍然需要合理的幾何結構。 它也不會替模型增加碰撞體積；當細節需要影響輪廓、接觸或近距離視差時，就要重新評估是否應保留幾何。 AI 生成法線圖，等於高低模烘焙嗎？不等於。 AI 可以生成看起來合理的表面凹凸，但要精準保留特定高模的細節，仍需要高低模對應、低模 UV 與正式烘焙流程。不能把任意一張紫藍色圖片直接當成正確法線資料。 在 Blender 中，法線圖通常會經過 Normal Map 節點再接入材質。切線空間法線圖需要對應的 UV，圖片應設定為 Non-Color，並確認與目標引擎的法線慣例相容。可參考 Blender 官方 Normal Map 節點手冊與烘焙說明；實際介面請對照自己使用的 Blender 版本。 五、Step 4 的材質與 UV，跟法線貼圖有什麼關係？法線貼圖其實只是材質系統的一部分。在 3D 製作中，常見的是 PBR（Physically Based Rendering，物理基礎渲染）材質。 用機甲來理解： 項目 用途 機甲範例 Base Color 決定基本顏色 紅色裝甲、白色胸甲、黑色關節 Metallic 表達金屬特性 金屬裸露區與非金屬塗層的差異 Roughness 控制反射的粗糙程度 低粗糙度反射較銳利，高粗糙度較模糊 Normal 模擬細小凹凸 刻痕、淺凹槽與裝甲紋路 Emission 表達自發光外觀 眼睛、能源核心與燈條 金屬零件表面若覆有一般非金屬漆，不能只因底下是金屬，就把整片外觀都設成裸金屬。Emission 能讓表面看起來發光，但是否照亮周圍、是否產生光暈，還取決於渲染器、燈光與後製設定。 UV 展開是什麼？想像把紙盒拆開攤平成一張紙，在紙上印上顏色與圖案，最後再折回紙盒。 UV 展開建立 3D 模型表面與 2D 圖片的對應關係。如果 UV 不正確，材質就可能拉伸、錯位或出現接縫。 因此，完整材質流程通常是： 模型整理 → UV 展開 → 產生或烘焙貼圖 → 設定 PBR 材質 → 檢查成果。 這也解釋了原本「使用 GPT 生成材質貼圖」需要補上的條件：產生一張金屬紋理圖片，不等於已經完成這台機甲的材質。 圖片仍要對應 UV，或經過投射、接縫修整與烘焙；Base Color、Roughness、Metallic、Normal 也必須各司其職。不能把帶著固定高光與陰影的彩色圖片，直接當成完整的 PBR 貼圖組。 「貼圖只能 512K」是什麼意思？原分享提到的「512K」需要特別注意，因為這不是清楚的貼圖像素尺寸寫法。它可能想表達 512×512 像素，也可能在描述檔案容量；沒有原始規格，無法確定。 兩者差異很大，而且貼圖解析度也不是越低越好： 常見像素尺寸 可以考慮的情境 512×512 部分小型物件或遠距離資產 為什麼要拆關節，還要設定骨架？因為目前做出來的機甲，可能只是一個外觀完整的模型。要讓它走路，就必須建立合理的活動結構。 機甲跟真人角色的綁定方式不完全相同。真人手肘彎曲時，皮膚會變形；但機甲的金屬裝甲，正常情況下不應該像橡皮一樣彎曲。 所以通常要讓不同部位可以獨立控制，例如胸甲、上臂、前臂、肩關節、大腿、小腿、膝關節與腳掌。這些可以是分離物件，也可以是同一網格內彼此不連通、由不同骨骼控制的剛體區塊。 接著設定旋轉樞紐、父子階層與活動限制： 手肘在合理角度內彎曲。 膝蓋不隨意向後折。 肩膀轉動時，肩甲配合移動。 腳掌落地時維持合理的接觸位置。 如果只把表面切開，沒有補齊遮住的零件、關節間隙與樞紐，動起來仍可能穿模或露出破洞。 有些機甲只需分離零件、旋轉樞紐與父子階層，就能完成基本動作；若使用骨架，也可以讓剛性裝甲跟隨單一骨骼，不一定要像皮膚一樣做平滑蒙皮變形。軟管、線材等需要彎曲的部分，則另行處理。 **機甲建模還涉及機械結構與運動設計。**拆分不正確，即使外觀很漂亮，動畫仍可能很奇怪。 Step 6：製作動畫，並到引擎中驗收骨架設定完成，還要在時間軸上安排動作。先從抬手、屈膝、腳掌落地等簡單測試開始，再做完整走路循環。 過程中要觀察裝甲是否穿模、腳是否滑動、重心是否合理，以及匯出後的骨架、材質與動畫是否一致。最後匯入 Godot 或其他目標環境，確認尺度、方向、播放與效能，才算走完這條流程。 能在 Blender 裡播放，不代表已完成遊戲整合；遊戲中的移動控制、碰撞與動畫切換，也需要另外設定與測試。 七、三種 AI 3D 建模流程，應該怎麼選？研究到這裡，我認為應該先決定用途，再選製作流程。 方案 A：快速展示型AI 圖片 → AI 生成白模 → AI 材質 → 3D 展示。 適合科幻角色展示、產品概念設計、靜態渲染與社群作品。若用於 3D 網頁，仍要視模型大小和裝置效能做適度整理。 優點是速度快、操作相對簡單；缺點是模型不一定適合動畫或遊戲。如果只想展示漂亮機甲，先走這條就很合理。 方案 B：遊戲資產最佳化型AI 圖片 → 高精度模型 → 整理低模 → UV → 烘焙法線貼圖 → PBR 材質。 適合遊戲場景物件、即時 3D、WebGL 展示，以及需要控制效能的資產。 優點是兼顧細節與幾何複雜度；缺點是需要理解 UV、拓樸與烘焙。這套流程不會自動讓機甲動起來。 方案 C：可動機甲型AI 圖片 → AI 生成白模 → 零件拆分與整理 → 關節設定 → 骨架／控制系統 → 材質 → 動畫。 適合機甲動畫、遊戲角色、戰鬥機器人與互動展示。優點是能建立真正可動的機甲；缺點是關節與動畫需要仔細調整，技術門檻最高。 這裡的排列是概念路線，不是唯一施工順序。需要改拓樸或拆件時，應先規劃好再定稿 UV 和烘焙；也可以先做簡單活動測試，再投入精細材質。     我現在做 Vibe Coding，不會只靠 Playwright 驗收了：SuperDesign × DESIGN.md × Codex Browser

    最近我一直在整理自己的 Vibe Coding 工作流。 以前的想法很單純：AI 寫完網站後，用 Playwright 跑一次；網站能開、按鈕能點、測試有過，大概就可以交差。 但最近接連研究 SuperDesign、Google 的 DESIGN.md，再加上 Codex 的 Browser use，我開始重新思考：AI 寫完網站之後，應該怎麼驗收？ 程式正確，不等於畫面正確。Build、TypeScript 與單元測試可以都通過，但它們不一定會告訴你手機版 CTA 是否被擋住、卡片間距是否一致，或頁面有沒有符合原本的視覺語言。 我現在會把流程拆成不同角色： 1SuperDesign → DESIGN.md → Codex 實作 → Codex Browser 動態驗收 → Playwright 核心回歸 → Deploy 這些工具不是互相取代，而是各自處理設計探索、規格、實作、人工判斷與重複測試。 為什麼只跑 Playwright，還不算完成 UI 驗收？Playwright 很適合確認固定流程能不能一再成功。例如使用者能不能登入、完成預約、修改資料，或走完結帳。這些條件可以明確寫成測試，也能放進每次 Pull Request 或部署流程裡。 但「按鈕是不是歪了」「手機版有沒有溢出」「畫面看起來是否符合品牌」通常需要結合上下文判斷。程式可以編譯成功，功能測試也可能通過，視覺層仍然不理想。 Playwright 也支援 Visual Comparison，可以用 toHaveScreenshot() 建立基準畫面並在後續執行時比對。這很適合穩定、重要而且值得守住的畫面；不代表每一個頁面、每一個 hover 狀態都要做成快照測試。快照基準仍需人工檢視與更新，而且不同作業系統、瀏覽器版本與字型可能造成差異。Playwright 官方文件 所以我不會把 Playwright 全砍掉，而是讓它專注在可以明確定義、必須重複通過的 Regression Test。 讓 SuperDesign、DESIGN.md、Codex 與 Playwright 各自負責一段 工具 在流程中的工作 適合處理的問題 SuperDesign 探索與比較設計方向 新頁面要採取什麼視覺方向？哪些設計變體值得比較？ DESIGN.md 記錄可重用的設計規格 顏色、字體、間距、元件與品牌原則要怎麼維持一致？ Codex 依規格實作並修正程式 如何把選定的設計方向落進現有程式碼？ Codex Browser 動態檢查實際畫面與互動 RWD、流程、Console 或 Network 是否有可見問題？ Playwright 自動守住關鍵 Regression 登入、預約、Checkout 或 CRUD 是否持續正常？ SuperDesign：先探索方向，再開始寫 UI以前我可能會直接跟 Coding Agent 說：「幫我把這個 Dashboard 做漂亮一點。」但「漂亮」的判斷太開放，Agent 可能直接選一套通用風格開始寫，最後很難確認它是否理解我的方向。 SuperDesign 可以放在實作前，協助分析既有介面、整理設計系統，並探索或比較不同的 UI 設計草稿。先看過幾個方向、選定適合的方案，再交給 Coding Agent 實作，會比要求它憑一句形容詞猜設計更容易對齊。SuperDesign Skill 官方專案 我會把這一步理解成「負責想」：先決定要往哪個方向走，不急著把第一個生成結果當成定案。 DESIGN.md：把視覺共識寫成可讀規格SuperDesign     最近看到 GSAP 官方推出一組 AI Agent Skills，我第一個反應不是「又多一個 AI 工具」，而是：這很適合放進 Vibe Coding 工作流。 現在用 Codex、Claude Code 或 Cursor 做網站，AI 通常很快就能生出 Landing Page。但開始要求它加上文字進場、卡片依序出現或 Scroll 動畫時，會動不代表動得好：動畫可能搶走閱讀焦點、手機版跑出畫面，或因為缺少清理而影響效能。 我想研究 GSAP，正是因為網站互動不只要「有動」，還要知道什麼時候動、怎麼安排節奏，以及怎麼照顧不同裝置的使用者。 GSAP 是控制網頁即時動畫的 JavaScript 函式庫如果你不是專門做前端動畫的，可以先把 GSAP 想成一套用來安排網頁元素動作的工具。它控制的是使用者瀏覽網站時，瀏覽器即時呈現的動畫；它不是 AI 影片生成器，也不負責把動畫輸出成 MP4。 像是標題逐行出現、圖片滑進畫面、卡片依序浮現、數字往上遞增、SVG 路徑動畫、按鈕微互動，或畫面隨著使用者捲動而演出，都是 GSAP 常見的使用情境。 如果你正在做 Landing Page、產品官網、活動網站、作品集或一頁式銷售頁，GSAP 可以幫你更精準地控制動畫的順序、時間與互動方式。它的 官方文件 也整理了 Core、Timeline、ScrollTrigger 與各類 Plugins 的使用方式。 GSAP 官方 AI Skills 把動畫實務帶進 Coding Agent以前請 AI 用 GSAP 做動畫，通常得自己描述需求，再期待模型能正確找出文件、安排程式結構並處理框架細節。現在 GSAP 官方把常見用法整理成 AI Agent Skills，可透過 npx skills add https://github.com/greensock/gsap-skills 安裝到 Codex 等支援的 Agent。 官方 repository 將 Skills 分成幾個方向： GSAP Core：gsap.to()、from()、緩動、stagger 等核心 API。 Timeline：管理多段動畫的先後、標籤與時間軸。 ScrollTrigger：處理捲動觸發、pin、scrub、refresh 與清理。 Plugins：說明各種 GSAP 外掛的使用方式。 React：涵蓋 useGSAP()、scope、cleanup 與 SSR 注意事項。 Frameworks：介紹 Vue、Svelte 等框架的生命週期與清理。 Performance：優先使用 transform，減少不必要的版面計算。 Utils：提供 clamp、mapRange、interpolate 等工具函式。 這件事值得注意的地方，不只是多了一套動畫函式庫，而是可以把官方累積的使用方式與常見注意事項，交給 AI Agent 在工作時參照。Skill 提供的是工作指引，不代表生成結果自然就正確；仍要看實際畫面、程式碼與裝置表現。 第一步：先請 AI 規劃，不要一開始就叫它加特效我會先把 AI 當成「動態設計顧問」，請它分析目前網站哪裡值得動。這一步能避免 Hero、卡片、按鈕和背景全部同時飛進來，讓動畫反而打斷閱讀。 可以先這樣下指令： 12345678910分析目前網站，找出 3 個最適合加入 GSAP 動畫的位置。不要為了動畫而動畫，先不要修改程式碼。優先評估：1.     AI工具 Vibe Coding
    AI Coding 技術債：寫程式快 10 倍，Temporary Fix 也可能快 10 倍

    最近看到一則工程師笑話：一家公司發現訂單偶爾會「消失」，工程師一路追查 Cache、Database、Replication、Redis、Kubernetes、Message Queue…… 查到最後才發現，整套龐大的企業架構，其實都在保護八年前的一個 Prototype。 最經典的是當年的 Commit： quick prototype, will redesign later 八年後，還是沒有 redesign。 我看完笑得很開心，笑完卻想到一件更可怕的事：如果這個故事發生在 AI Coding 時代呢？ AI 讓 Prototype 更快，理解系統卻沒有變快以前，一個工程師可能花兩個星期寫出 Prototype。現在用 Codex、Claude Code 或其他 AI Agent，一個下午就可能做出雛形：需求丟進去，Agent 開始寫程式、建立資料庫、串 API、部署 Cloudflare、接 Google Sheet、做登入、補後台。 跑起來、測一下、能用、上線。爽。 問題是，我們把「做出軟體」的速度提高了，不代表「理解系統」的能力也跟著提高。以前自己寫三千行程式碼，至少大概知道東西放在哪；現在 Agent 一個晚上可能改了幾十個檔案、加上套件、補 Issue，隔天打開 GitHub，看起來很厲害，卻只能祈禱不要壞。 AI Coding 加速的是產出，不會自動替你補上理解、判斷與維護能力。 真正麻煩的不是程式寫錯，而是沒人知道它為什麼能跑AI 寫錯程式，通常還有訊號：測試失敗、CI 變紅、網站掛掉。至少我們知道某處出了問題。 更難處理的是一個「現在可以跑，但沒有人真正理解為什麼可以跑」的系統。它可能沒有明顯錯誤，還開始接到客戶、處理預約或帶來收入。這時候有人提議重構，第一個反應常常不是「好」，而是「現在不是能跑嗎？」 恭喜，第一筆技術債誕生了。 接著需求和臨時修補一層一層疊上去： 「這裡先加個判斷。」 「那邊先 Workaround。」 「這個欄位先不要動。」 「這個 Workflow 不知道為什麼不能刪。」 「這段是 AI 寫的，先不要碰。」 最後 README 可能出現一句 DO NOT MODIFY THIS SECTION. 沒有人知道原因，但大家都很尊重它。 Prototype 最危險的時刻，未必是它出 Bug，而是它開始被依賴、開始賺錢，卻沒有人敢改。 AI 降低開發成本，沒有自動降低維護成本以前一年可能做三個 Prototype，現在一年可以做三十個。這些雛形不一定都會留下來，但只要其中一部分開始接觸真實使用者、營運流程或收入，它們就從「先試試看」變成需要長期照顧的系統。 如果每次都只追求先跑起來，AI 就可能讓臨時作法累積得更快：一年多做了十倍 Prototype，也可能多留下十倍需要理解和維護的東西。效率提高了，技術債也能跟著自動化累積。🤣 所以 Vibe Coding 下一階段重要的能力，不只是「怎麼叫 AI 幫我寫程式」，而是「怎麼讓 AI 幫我建立一套未來還敢修改的系統」。這兩件事差很多。 把專案記憶留在 Repository，讓下一個 Agent 接得住比較大的 AI Coding 專案，我會開始要求 Agent 做幾件以前覺得很囉嗦的事： 先寫規格、拆 Issue： 把目標、範圍與完成條件留下來，讓每次修改都有依據。 記錄架構決策： 說明為什麼採用某個做法，以及有哪些限制，避免未來的人只看到程式碼、看不到背景。 補測試並做 Code Review： 不只確認功能能跑，也檢查變更有沒有破壞原本行為；重要修改還可以請另一個模型做對抗性驗證。 重要修改先 Commit： 留下可追蹤的變更邊界，搞砸時才知道從哪裡回復。 更新 README 與必要文件： 把執行方式、關鍵流程和已知限制放在下一個接手者找得到的地方。 更重要的是，別只問 AI：「可以跑嗎？」也問：「半年後，另一個完全不知道背景的 Agent 接手，它看得懂嗎？」 未來維護程式碼的人可能不是現在的你，也可能是下一代 Codex、Claude Code，或另一個從沒參與過這個專案的 Agent。Git、Issue、README、測試與 Architecture Decision Record，不只是寫給工程師看的文件，也是留給下一個 Agent 的專案記憶。 以前寫文件，是怕工程師離職；未來寫文件，可能是怕 AI 換模型。模型會變，Agent 的 Session 也可能重新開始。真正能留下來的，不是它「記得什麼」，而是 Repository 裡留下了什麼。 所以我現在看
